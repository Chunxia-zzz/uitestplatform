# URL 抓取并导入元素：能力评估

| 项 | 内容 |
|---|---|
| **评估对象** | 「用户输入一个 URL → 自动抓取解析页面元素（文本/图片/链接/表单）→ 导入平台」 |
| **评估日期** | 2026-10-19 |
| **结论** | ❌ **当前不能实现**；🟡 **底层依赖齐全，缺一层应用功能**；技术上可部分实现 |
| **核验方式** | 代码检索 + 真实页面扫描（`scripts/probe_dom_capability.py`） |

---

## 1. 结论摘要

| 判断 | 说明 |
|---|---|
| **现在能不能点一下就用？** | **不能**。没有任何"输入 URL → 返回元素清单"的入口，也没有存放"抓取结果"的地方 |
| **技术上做不做得到？** | **做得到**。Playwright 已是运行期依赖，会话/目标/定位符/元素写入全都在，缺的只是"扫描 + 候选 + 导入"这一层 |
| **是"缺一个开关"还是"缺一个模块"？** | **缺一个模块**：扫描服务 + 候选模型 + 批量导入 + 前端预览，四个环节都要新建 |
| **最大的风险不是技术** | 是**元素库被污染**：一次导入几十个 `div`，人工维护的元素树就废了。所以必须"候选池 → 人工筛选 → 入库"，不能直接写 |

---

## 2. 逐项对照：需求链路上缺什么

| # | 环节 | 现状（代码依据） | 缺口 |
|---|---|---|---|
| 1 | **输入 URL 并打开页面** | ✅ 有：`navigate` 动作 + `execution_target.base_url` + `wait_until` | 无（会话能力现成） |
| 2 | **抓取整页 DOM** | ❌ **无**。`grep page.evaluate` 只有两处 `window.scrollTo`；`element_list` 只对**已绑定的元素**取列表（最多 200 条，只返回 text/visible） | 需要新增"按 URL 扫描"的服务 |
| 3 | **解析成结构化元素**（tag/文本/图片/链接/表单属性） | ❌ **无**。没有任何 `querySelectorAll`、`content()`、`innerHTML` 的调用 | 需要一段抓取脚本 + 归一化逻辑 |
| 4 | **候选元素的存放** | ❌ **无**。`element` 表是**人工维护的逻辑元素**（`element_name` 必填、同父下唯一），不适合当抓取结果的草稿箱 | 需要 `page_snapshot` / `candidate_element` 表（或"不落库、只返回"的轻方案） |
| 5 | **自动生成定位符** | ❌ **无**。现有 11 种定位类型是"人工填写 + 一键验证"，没有"从 DOM 属性推导候选 + 稳定性评分"的算法 | 需要定位符生成器（优先级规则见 §4.3） |
| 6 | **批量导入** | ⚠️ **半有**：`locator_service.create_bulk()` 服务层已存在（单元素最多 50 条），但**没有暴露批量端点**；元素只有单条 `POST /elements` | 需要 `POST /projects/{id}/elements/import` 之类的一次性提交 |
| 7 | **前端预览与勾选** | ❌ **无**。现有页面都是"录入/编辑"，没有"扫描结果预览 + 勾选导入" | 需要新增一个页面 |

> 一句话：**1 有，2/3/4/5/7 没有，6 有一半。**

## 3. 实测：如果做，能抓到什么、覆盖率多少

用现有 Playwright 依赖对 fixtures 三个页面做了真实扫描（`scripts/probe_dom_capability.py`，只统计可见元素）：

| 页面 | 可见元素 | 强定位符 | 中 | 弱 | 不可用 | 主导定位方式 |
|---|---|---|---|---|---|---|
| `login.html` | 7 | **6（86%）** | 0 | 1（14%） | 0 | testid×4、id×2、text×1 |
| `todo.html` | 8 | **7（88%）** | 0 | 1（12%） | 0 | testid×4、id×3、text×1 |
| `locators.html` | 16 | 5（31%） | 1（6%） | **10（62%）** | 0 | class×5、text×5、id×3、testid×2 |

**怎么读这张表**：

- 强定位符 = `data-testid` / `id` / `name`，直接可用；
- 弱 = 只有 `class` 或纯文本，页面一改就断；
- `locators.html` 是**故意没有任何语义属性**的测试页，所以弱定位占 62%——这恰恰是真实老页面的常见状态。

→ **覆盖率取决于被扫页面的规范程度，不是抓取技术**。有 `data-testid` 的页面能到 85%+；纯 `div + class` 的老页面，一半以上只能生成脆弱定位符。

**各类元素能不能抓**：

| 类型 | 能否抓到 | 抓成什么 |
|---|---|---|
| 文本 | ✅ | 叶子节点 `innerText`（截断 60 字符） |
| 图片 | ✅ | `img[src]` + `alt`（可作 `alt` 定位类型） |
| 链接 | ✅ | `a[href]` + 文本（用 `css` / `text` 定位） |
| 表单 | ✅ | `input/select/textarea` 的 `name`/`placeholder`/`type`/`aria-label` |
| 按钮 | ✅ | `button` + `type` + 文本 |
| 容器 div | ✅（但不该导） | 只有 `class`，导进去会让元素树不可用 |
| canvas / WebGL | ❌ | 没有 DOM 结构，只能截图像素比对 |
| 封闭 Shadow DOM | ❌ | 当前无穿透能力 |
| 虚拟滚动未渲染项 | ❌ | 只能抓到当前视口渲染出来的 |
| 伪元素 `::before` 内容 | ❌ | 不在 DOM 文本里 |

## 4. 如果要实现：可覆盖范围与前提

### 4.1 可覆盖（阶段一能交付的范围）

- 静态页 / 服务端渲染页 / 常规 SPA（等 `networkidle` 后扫描）
- 文本、图片、链接、表单控件、按钮的**候选清单**
- 每个候选给出 **1~3 条定位符建议 + 稳定性等级**
- 人工勾选后**批量导入**到现有元素库

### 4.2 前提条件

| 前提 | 说明 |
|---|---|
| 页面可访问 | 网络可达、证书可忽略（`ignore_https_errors`） |
| 需要登录的页面 | 用 `execution_target.options.storage_state` 先登录一次再扫描 |
| 动态渲染 | 必须等 `networkidle`，必要时在扫描前注入等待/滚动 |
| 有项目归属 | 元素必须挂在某个 `project_id` 下（当前模型如此） |
| 反爬/验证码 | 无解，只能人工先过 |

### 4.3 定位符生成优先级（建议规则）

```
data-testid → id → name → role+aria-label → aria-label → placeholder
→ alt → title → text（叶子且长度 2~30）→ css（nth-of-type 路径）
```

评分：前 6 档为"强/中"，`text` 与 `class` 为"弱"，纯容器不给定位符。

### 4.4 不建议的做法

**不要直接写进 `element` 表**。原因：

1. `element.element_name` 必填且同父下唯一 → 自动命名会产生 `div-1…div-50` 这类垃圾名；
2. 元素库是**长期资产**（用例步骤靠它引用），一次导入 50 个容器节点会让树彻底不可用；
3. 删除需要逐个处理引用（`ElementReferenced`），清理成本高。

正确姿势：**候选池（不入库）→ 人工勾选 → 只导入被选中的**。

## 5. 建议的实现路径（分两阶段）

### 阶段一：轻量扫描（不改表，1 个端点 + 1 个页面）

```
POST /api/v1/projects/{id}/element-scan
body: { "url": "...", "max_elements": 200, "include": ["text","image","link","form","button"] }
→ 200 { "candidates": [ { tag, name, text, strength, locators:[{type,value}] } ],
        "stats": { total, strong, medium, weak },
        "warnings": [...] }        # 注意：**不落库**
```

- 扫描复用 `SessionManager` + `PlaywrightAdapter`（会话、headless、超时都能沿用）；
- 扫描能力应做成**适配器诊断方法** `scan_dom()`，与 `probe_locator()` 同类，**不进 `action_catalog`** ——
  动作字典只装"用例能编排的步骤"，扫描是"平台自身能力"（这是 M2 F-M2-3 定下的原则）；
- 前端新增 `/scan` 页：输入 URL → 预览表格（勾选 + 编辑名称）→ 「导入选中」→ 循环调现有 `POST /elements` + `POST /locators`；
- 同时把 `create_bulk` 暴露成端点，减少导入时的请求数。

**改动面**：1 个服务 + 1 个端点 + 1 个页面 + 约 10 条测试。

### 阶段二：可追溯的扫描（加表）

- `page_snapshot(id, project_id, url, taken_at, stats)` + `candidate_element(snapshot_id, ...)`；
- 支持"两次扫描对比"（页面改版后哪些元素消失/新增）；
- 支持增量导入与去重（按 `(tag, locator_value)` 判重）。

**改动面**：2 张表 + 1 个迁移 + 导入冲突策略 + UI。

## 6. 与既有决策的关系（需要你确认）

| 决策 | 与本需求的关系 |
|---|---|
| **D14 不做元素拾取器** | 拾取器是"在页面点选"；本需求是"按 URL 批量扫描"。**技术上不冲突，但都属于"自动生成定位符"**。做本需求前建议明确：D14 的边界是"不做交互式点选"，不含"批量扫描" |
| **D16 不做跨项目元素共享** | 不影响 |
| **D26 不做平台管理功能** | 扫描导入属于"资产生产"，不在被砍范围内 |

## 7. 最终判断

| 问题 | 回答 |
|---|---|
| 现有功能能否实现？ | **不能**。缺扫描入口、候选模型、定位符生成、批量导入、预览页面五个环节 |
| 是否技术上可行？ | **可行**。Playwright 与写入链路都在，属于"补一层应用功能"，不是"换技术栈" |
| 能部分实现吗？ | **能**。阶段一（不落库的扫描 + 勾选导入）就能覆盖"文本/图片/链接/表单/按钮"，前提是页面能访问、有项目归属、接受"弱定位符需要人工复核" |
| 最大风险 | 元素库被自动生成的容器节点污染 → 必须"候选池 + 人工筛选" |
